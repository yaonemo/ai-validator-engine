# 完整闭环：从「项目填表」到「自动校验→任务反馈→复盘」

> 这是本项目的「杀手锏」。前面介绍的是手动跑校验；本章讲怎么搭一条**全自动流水线**，让项目端填表、AI 端自动校验、飞书任务通知到人、每天自动复盘。**搭一次，之后全自动。**

闭环全景图：

```
项目端                           AI 端（Hermes）                        管理端
──────                            ───────────                       ──────────
在飞书多维表格表单里提交  ──▶  定时扫描待校验记录  ──▶  自动校验  ──▶  校验通过/需修改
（填 Excel 附件或贴链接）          │                          │
                                │                          ├─▶ 飞书「任务」通知提交人
                                │                          │      （哪一行、哪个字段、怎么改）
                                │                          └─▶ 更新表格「校验状态」
修改后重新提交  ◀─────────────────┘
                                │
                                └─▶ 每日复盘（错误模式/未完成清单/AI建议）
                                        ├─▶ 事业部汇总
                                        └─▶ 项目/事业部/总部三层送达
```

---

## 一、准备飞书多维表格（收集表）

项目端通过一个「表单」提交数据，数据落进一张多维表格。这张表就是整个闭环的入口。

> **字段清单、建表步骤、表单入口开启方法，见 `docs/飞书收集表模板说明.md`**（含可导入的表头模板）。本章不再重复，只讲它如何接入自动校验流水线。

---

## 二、配置自动校验（Hermes 侧）

### 1. 让 AI 生成你们部门的校验配置

先按 `安装到智能体.md` 装好 Hermes，再让 Hermes 按 `validator-officer` 技能生成规则 JSON，人审确认后存为 `你的规则.json`。

### 2. 定时扫描待校验记录

Hermes 挂一个**定时任务**，周期性扫描收集表里「校验状态」为空的记录，自动校验。

```bash
# cron 表达式示例：每 2 分钟扫一次（频率可按业务量调整）
*/2 * * * *
```

> 扫描逻辑：读收集表全量记录（注意分页，别只读第一页），过滤出「校验状态」为空的，逐条校验。

### 3. 按提交方式自动校验

每条待校验记录根据「文档提交方式」分流：
- **飞书线上链接** → 解析 wiki / bitable 记录链接 → 校验表格
- **线下 Excel 附件** → 下载附件 → 校验文件

校验失败（token/网络/附件下载失败）要**区分系统问题 vs 数据问题**：系统问题状态保持「待校验」让定时任务自动重试，并告诉提交人「是系统问题，不是您数据的问题」，绝不能误判成数据不通过。

---

## 三、飞书「任务」反馈（通知到人）

校验完，通过**飞书任务**精准通知到提交人——这是本方案的关键设计：**每条反馈只发给对应提交人，且直接告诉他怎么改。**

| 结果 | 任务标题 |
|------|---------|
| ✅ 通过 | 「XX项目车位信息校验通过」 |
| ❌ 需修改 | 「XX项目车位信息需修改，请点击查看详情」 |

### 内容要点（给填报人看的，必须通俗）

- **说人话**：明确指出「哪一行、哪个字段、当前值、应该怎么改」
  - ❌ 「格式错误」
  - ✅ 「第 12 行『产权人』填了『张伟』，但这条是开发商保留车位，产权人应是公司名，请改成 XXXX 公司」
- **篇幅控制**：飞书任务描述有上限（约 3000 字符），超长的截断并提示「完整内容请看收集表『修改建议』列」

### 技术实现（Hermes 侧）

用飞书开放平台「任务」接口创建任务，分派给提交人：

```bash
lark-cli task +create \
  --summary "项目XX车位信息需修改" \
  --description "第12行产权人应为公司名…" \
  --assignee <提交人open_id> \
  --as bot
```

> 任务创建失败可回退为私信（需对方互动过 Bot）。

---

## 四、修改后重提 → 自动复核

项目按反馈改完，重新在表单提交 → 定时任务又扫到这个新记录 → 自动复核 → 通过则任务通知「校验通过」。**闭环自洽，无需人盯。**

---

## 五、每日复盘（三层送达）

数据收得差不多后，用 `analyst-officer` 技能每天自动复盘，**分三层**送达不同人。

### 复盘报告包含 4 块

1. **事业部汇总**：今日提交 / 通过 / 修改中（只列有活动或有积压的事业部，不刷屏）
2. **多次提交仍未通过**：≥2 次未过的项目（≥3 次逐条列出，2 次合并，控制篇幅）
3. **错误模式**：新出现 / 上升中 / 持续存在的错误类型（主动发现规则之外的问题）
4. **AI 改进建议**：大模型结构化思考，给出话术改进方向

### 三层送达

| 层级 | 送达对象 | 内容 |
|------|---------|------|
| 项目层 | 提交人 | 逐条修改建议（见第三节） |
| 事业部层 | 事业部负责人 | 本事业部汇总 + 跟进清单 |
| 总部层 | 总部运营 | 全集团汇总 + 错误模式 + AI 建议 |

> 再往前一步：复盘发现的**高频错误 → 改规则/话术 → 提交人更容易过**，这就是「越用越聪明」。别把「拦截了多少错误」当复盘的亮点（那是核对的功劳）；复盘的亮点是「**发现问题、指导改进、沉淀经验**」。

---

## 六、上线检查清单

- [ ] 多维表格字段齐全（含「校验状态」「修改建议」）
- [ ] 表单入口已开，项目端能提交
- [ ] 校验配置 JSON 人审通过，能加载、跑出报告
- [ ] 定时任务已挂，每 2 分钟能扫到待校验记录
- [ ] 校验收到的通知是「人话」，指出行号/字段/怎么改
- [ ] 复盘报告能分层送达事业部/总部
- [ ] 用一份真实数据跑过完整回归（从提交到复盘全通）
