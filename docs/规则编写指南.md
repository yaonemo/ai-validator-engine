# 规则编写指南

规则文件是一个 JSON，**规则 = 全部业务逻辑**。引擎读它来检查数据。

## 整体结构

```json
{
  "meta": { "名称": "...", "版本": "1.0", "适用业务": "...", "规则来源": "..." },
  "structure": { "标准表头": ["列1", "列2", ...] },
  "项目名提取": { "字段": "xxx", "策略": "most_frequent", "兜底": "文件名" },
  "组织关键词": ["公司", "集团", ...],
  "字段校验": [ ... 单字段规则 ... ],
  "逻辑校验": [ ... 字段间关系规则 ... ],
  "场景校验": [ ... 组合场景规则 ... ]
}
```

## 各部分说明

### 1. meta（元信息）
记录规则名称、版本、来源，方便别人看懂这份规则是哪来的。

### 2. structure.标准表头
你的数据表格的列名，**必须和 Excel 表头一致**（引擎按列名读数据）。
例：`["行号", "所属事业部", "车场名称", ...]`

### 3. 字段校验（最常见）
每条规则格式：

```json
{
  "id": "F01",
  "type": "required",
  "field": "row_num",
  "severity": "error",
  "message": "行号列为空，必须填写连续编号"
}
```

**type 可选值：**

| type | 作用 | 示例 |
|------|------|------|
| required | 必填（条件满足时跳过） | 行号不能为空 |
| in_list | 值必须在列表内（空值跳过） | 车位类型必须∈[普通车位,机械车位,...] |
| numeric | 必须是数字 | 车位面积必须是数字 |
| if_then | if 成立时 then 断言必须成立 | 状态=已出售 则 产权类型≠开发商保留 |
| personal_name_warn | 疑似个人姓名→警告 | 产权人应是公司名 |
| org_name_check | 必须是组织/公司名 | 产权人=开发商时必须是公司名 |
| not_contains_any | 值不能包含任一关键词 | 车位位置不能含「地库」 |
| keyword_not / keyword_if / keyword_and | 备注关键词触发检查 | 备注含「出租」时状态必须=已出售 |

**op 操作符**（条件用）：`eq`（等于）、`neq`（不等于）、`in`（在列表）、`not_in`（不在）、`contains`（包含）、`not_blank`（非空）

### 4. 逻辑校验（字段之间的关系）
例：「车位状态=空置 → 收费规则名称必须填 \」

```json
{
  "id": "L01",
  "type": "if_then",
  "if": { "field": "spot_status", "op": "eq", "value": "空置" },
  "then": { "field": "fee_name", "op": "eq", "value": "\\" },
  "severity": "error",
  "message": "车位状态为'空置'但收费规则名称不是'\\'，当前值: {value}"
}
```

### 5. 场景校验（组合场景）
多个字段组合的检查，按实际业务写。

## message 怎么写

**要写人话**，让填表人一看就懂改哪里：
- ❌ 差：「数据错误」
- ✅ 好：「车位状态为'已出售'但产权类型为'开发商保留'，逻辑矛盾，请核实」

## 校验字段命名约定

建议用英文短名映射表头：
- `row_num` 行号、`division` 事业部、`parking_name` 车场名称
- `spot_type` 车位类型、`spot_status` 车位状态、`spot_space` 车位空间、`pos` 车位位置
- `property_type` 产权类型、`property_owner` 产权人、`fee_name` 收费规则名称、`fee_type` 收费规则类型

## 快速上手建议

**不要手写**。把标准文档交给 AI（见 `技能包说明.md`），让 AI 生成初稿，你再微调。手写 JSON 容易漏规则，AI 生成 + 实测校准是最高效的路径。
