# 核对技能包（Validator Officer）

> 三角色之一：**培训**（规则→填表说明）→ **核对**（数据→校验）→ **复盘**（数据→洞察+报告+学习）
> 本技能是「核对」角色的方法论：把部门标准文档变成可执行的校验配置。

## 这个技能是干什么的

把任何部门的**标准/规则文档**（人话写的，可能几百到几千字）变成一套**可执行的校验体系**（检查清单 JSON），配合校验引擎对数据做稳定校验。

**核心思想：AI 思考 + 引擎执行**
- AI（你）负责思考：读文档 → 拆解出检查项 → 生成「校验配置 JSON」
- 校验引擎负责执行：照清单逐条检查，对错 100% 可复现
- 配套引擎：仓库根目录 `validate_config_engine.py`
- 参考配置：仓库 `example/parking_check_rules.json`

## 触发条件

用户说以下任意一种：
- "帮我把XX标准/规则做成校验"
- "根据这份文档生成校验体系"
- "我们部门有XX规范，想自动检查数据"
- "复制核对"（把现有配置换成新部门规则）

## 工作流程

### 第 1 步：读标准文档，理解业务

通读部门提供的标准文档，回答三个问题：
1. **这份标准要管什么数据？**（对象、字段、表格结构）
2. **每条规则想达到什么目的？**（理解意图，不是照抄文字）
3. **哪些是可执行校验的？哪些只是说明性文字？**（说明性文字不进清单）

### 第 2 步：动脑拆解（核对的思考）

把文档拆成**检查项**，从 5 个层面思考：

1. **结构层**：数据表长什么样？标准列名、列数、数据起始行、示例行特征
2. **字段层**（每个字段问自己）：
   - 必填吗？（空值=数据缺失 → error）
   - 有预定义值域吗？（不在列表中 → error，不是 warning）
   - 有格式要求吗？（纯数字、不能含中文、固定格式）
   - 空值时什么情况合法？（如"无"、反斜杠"\"、"全体业主"）
3. **联动层**（字段与字段之间）：
   - 状态 A → 字段 B 必须/不能是 X？
   - 备注含某关键词 → 触发什么场景规则？
4. **分级层**（error vs warning）：
   - **error（必须改）**：数据缺失、填错、逻辑矛盾、不在预定义列表
   - **warning（建议改）**：疑似有误但不确定（如个人姓名疑似）、建议优化
5. **盲区层（关键思考）**：
   - 文档**没写**但明显该检查的 → 主动补充，在"待确认清单"里说明"依据推断"
   - 文档**自相矛盾**或**有歧义**的 → 标记为"需业务确认"

### 第 3 步：生成校验配置 JSON（检查清单）

输出三样东西：
1. **校验配置 JSON**（引擎直接用的检查清单）
2. **规则解读**（人话说明：每个检查项为什么这么定、依据文档哪句话）
3. **待确认清单**（盲区、歧义、需要业务专家拍板的点）

**配置文件结构模板：**

```json
{
  "meta": {"名称": "业务名称校验", "版本": "1.0", "适用业务": "XX", "规则来源": "《部门标准文档名》"},
  "structure": {
    "标准表头": ["列1", "列2", "..."],
    "表头别名": {},
    "数据起始行": 3,
    "示例行过滤": {"字段": "row_num", "包含关键词": ["示例"]},
    "字段映射": {"key1": "列1", "key2": "列2", "..."}
  },
  "项目名提取": {"字段": "key", "策略": "most_frequent", "兜底": "文件名"},
  "组织关键词": ["公司", "集团", "企业", "单位", "...", "管理"],
  "字段校验": [],
  "逻辑校验": [],
  "场景校验": []
}
```

**检查项类型速查（type 字段）：**

| 类型 | 作用 | 适用 |
|------|------|------|
| `required` | 必填（unless 可排除） | 缺失检查 |
| `in_list` | 值必须在列表 | 值域检查 |
| `not_contains_chinese` | 不含中文 | 编号格式 |
| `numeric` | 纯数字（allow_values 例外） | 面积/金额 |
| `if_then` | 条件成立→断言成立 | 字段联动 |
| `personal_name_warn` | 疑似个人姓名→warning | 产权人类别 |
| `org_name_check` | 必须是组织名 | 公司名检查 |
| `not_contains_any` | 不含任一关键词 | 排除检查 |
| `keyword_not` | 备注含词→目标字段不含禁词 | 场景规则 |
| `keyword_if` | 备注含词且条件成立→报错 | 场景规则 |
| `keyword_and` | 备注含词且条件成立→报错 | 矛盾检测 |

**操作符（op）**：`eq` / `neq` / `in` / `not_in` / `contains` / `not_blank`

**消息模板**：`{value}`=当前值，`{字段key}`=字段值。提示语必须**大白话+具体到怎么改**：
- ❌ "格式错误"
- ✅ "第X行编号「C区003」含中文，请改成英文+数字，如 CS-003"

### 第 4 步：交付给业务专家人审

生成配置后**必须**提示用户：
1. 请业务专家核对检查项是否覆盖所有业务要求
2. 重点确认"待确认清单"里的盲区/歧义
3. 确认后启用配置 → 校验引擎开始工作

**人审环节不能省**：AI 起草、人确认，这是业务落地的标准动作。

## 参考范例：车位信息校验配置

完整配置：仓库 `example/parking_check_rules.json`

高频检查项示例：
- 行号：必填（error）
- 类型/状态/空间/位置/产权类型：必须在预定义列表（error）
- 编号：不含中文（error）
- 面积/单价：纯数字（error）
- 产权人联系方式：必填（全体业主时除外）（error）
- 状态=已出售 → 产权类型≠开发商保留（error）
- 状态=开发商自有 → 产权人必须是组织名（error）
- 产权=全体共有 → 产权人=全体业主（error）
- 备注含"物业承包" → 状态=租赁、产权=开发商保留（error）
- 备注含"业主相互租赁" → 状态=已出售（error）
- 状态=空置 → 使用人=无、收费字段=\（warning/error）
- 产权=开发商保留 → 产权人疑似个人姓名（warning）

**判断组织名的关键词**（可配置）：
公司、集团、企业、单位、委员会、政府、局、处、中心、院、学校、医院、银行、基金、协会、商会、开发、地产、置业、投资、建设、物业、管理

## 注意事项（Pitfalls）

1. **不要用 LLM 直接逐行校验数据**——幻觉、漏检、前后不一致。LLM 只负责生成配置，校验交给引擎
2. **"不在预定义列表"必须是 error 不是 warning**
3. **数据缺失类（行号、联系方式、电话）必须是 error**（不是 warning）
4. **空值合法场景要写清楚**：如"无"、反斜杠"\"、"全体业主"等例外值要放进规则（allow_values / unless）
5. **示例行过滤**：模板自带的示例数据行要跳过（第一列含"示例"/"字段说明"）
6. **字段映射注意长名优先**：如"产权人联系方式"要先于"产权人"匹配，避免短名吃掉长名
7. **反斜杠转义**：JSON 里一个反斜杠写成"\\"
8. **先跑真实数据回归测试**：新配置生成后，用一份真实数据验证检查项数量和准确率，再投入使用
9. **第一列表头（A1）为空**时：如果其余列都正确，只提示补「行号」，不要报「列数不正确」

## 验证清单

- [ ] 配置 JSON 能被引擎加载（无语法错误）
- [ ] 每个字段的必填/值域/格式检查齐全
- [ ] 字段联动关系覆盖（状态↔产权↔产权人↔使用人）
- [ ] 备注关键词场景规则覆盖
- [ ] error/warning 分级合理（缺失和填错=error）
- [ ] 提示语是大白话，告诉用户"怎么改"
- [ ] 待确认清单已交付业务专家
- [ ] 用真实数据跑过回归测试
