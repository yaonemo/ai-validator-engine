# 复盘技能包（Analyst Officer）

> 三角色之一：**培训**（规则→填表说明）→ **核对**（数据→校验）→ **复盘**（数据→洞察+报告+学习）
> 本技能是「复盘」角色的方法论：在核对结果之上，用 AI 发现规则之外的问题，并沉淀经验。

## 这个技能是干什么的

把校验引擎的校验结果（issues）+ 原始数据摘要，变成**规则之外的洞察和建议**，并沉淀为学习档案，让系统越用越聪明。

**与核对的分工（一句话区分）：**
- **核对** = 「按规则查」：对就是错，错就是错，判断对错（100% 稳定可复现）
- **复盘** = 「看数据找事」：发现规则没写的问题，提供洞察和建议，**不下对错结论**

**角色边界（重要，别搞混）：**
- 「告诉提交方哪里要改」= 核对（判定 + 通知），**不是复盘**
- 复盘的产出给**管理层/评审**：发现、规则改进建议、风险提示
- 复盘的输出不是「修改指引」，是「洞察」

## 触发条件

用户说以下任意一种：
- "做复盘 / 洞察 / 数据二次分析"
- "让 AI 越用越聪明 / 自我总结学习 / 学习档案"
- "发现规则之外的异常 / 跨项目对比"
- "周报 / 三层报告"

## 架构与数据流（核心思想：统计用代码，洞察用 AI）

```
项目Excel + 校验配置JSON
   ↓
① 核对引擎 validate_file() → issues（哪行/哪个字段/哪条规则/error/warning）
   ↓
② 复盘统计层（Python，无AI，稳定）
   - 错误画像：按字段/按规则/按严重度分布
   - 数据摘要：各字段填充率、值分布TOP5
   - 可疑信号：数值全相同/号码重复/编号重复/占位符泛滥
   ↓
③ 复盘洞察层（LLM，每次）
   - 规则外异常：数据太完美、批量复制痕迹、跨项目数据串入
   - 规则盲区：现有规则查不出的新错误类型 → 规则改进建议
   - 培训反哺：连续多个项目高频错误 → 培训材料建议
   ↓
④ 学习档案（JSON，自动追加）
   - 每次复盘沉淀经验 → 下次复盘先读档案 → 越用越聪明
   ↓
⑤ 分层报告
   - 项目层：简洁明确（对/错 + 怎么改）
   - 事业部层：共性问题 + 可落地行动建议
   - 总部层：对比 + 趋势 + 风险
```

## 复盘四类洞察（学习什么）

1. **错误模式**：本次数据错得最多的是什么？→ 记录
2. **规则盲区**：发现规则没覆盖的新错误？→ 建议补充规则
3. **培训反哺**：某个字段连续多个项目错误率都高 → 说明培训没讲清 → 建议加强
4. **异常规律**：跨项目对比发现规律（如临截止日期提交的错误率更高）

## 学习档案结构

一个结构化 JSON，每次复盘后追加一条：

```json
{
  "项目": "飞龙景苑",
  "时间": "2026-08-03",
  "错误分布": {"产权类型": 44, "使用人电话": 1},
  "新错误模式": ["收费单价带单位'150元/月'，规则未覆盖"],
  "规则改进建议": ["补充F19.2：单价含'元'字报错"],
  "培训建议": ["产权类型场景需在培训材料加强"]
}
```

下次复盘时，AI 先读档案 + 当前结果 → 对比输出：
- "这个项目和上次 XX 的错误模式相似"
- "产权类型错误已连续 3 个项目偏高"

## 三层报告格式

**给总部：**
- 全局完成率、数据质量综合评分
- 各事业部排名（完成率 + 质量分）
- 本次收集反映出的系统性问题和建议
- 一句话总结

**给事业部：**
- 管辖项目完成情况（已完成 X 个，待修改 X 个）
- 红灯项目清单（具体项目、什么问题）
- 管辖项目常见错误 TOP3
- 需要重点关注的项目和问题

**给项目：**
- 提交的数据：通过 X 条，需修改 X 条
- 每一条需修改的具体位置和修改方法
- 全部通过则：✅ 已通过，无需任何操作

## 必须守住的边界

1. **学习不能自动改规则**——所有规则改进建议必须人确认后生效（防止 AI 学偏）
2. **学习档案可追溯**——每条建议注明依据哪次校验
3. **规则外洞察流向管理层，不给一线**——一线填完通过了再收到「疑似复制」只会烦，这是管理问题

## 注意事项（Pitfalls）

1. **不要逐行让 LLM 思考**：1000 行数据 = 1000 次 AI 调用，又慢又贵又不稳定。引擎先查完（秒级），AI 只看整体结果做洞察
2. **没发现异常就说没有**，不要强行编
3. **每条发现附上具体数据和对应项目名称**，语气是「帮你发现问题」，不是「批评谁做得不好」
4. **LLM 复杂请求注意输出格式**：要求 JSON 输出时加 `response_format` 强制，且 max_tokens 要给足（推理模型会先消耗大量 token）
5. **报告分层**：项目层只给「第X行Y字段填错应填Z」；事业部层每条建议必须可落地（谁/做什么/怎么验证），禁止空话
